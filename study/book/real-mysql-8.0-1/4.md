# 4장 아키텍처

아래는 메모를 **Real MySQL 4장(InnoDB 아키텍처·버퍼 풀·로그·잠금)** 흐름에 맞게 재구성한 정리입니다. 표현은 면접이나 기술 문서에 바로 활용할 수 있도록 다듬고, 일부 용어와 동작은 정확하게 보완했습니다.

## InnoDB 핵심 구조 정리

InnoDB는 디스크 기반 데이터를 다루지만, 실제 성능과 안정성은 메모리 구조인 **버퍼 풀**, 복구를 위한 **Redo/Undo 로그**, 그리고 동시성 제어를 위한 **락과 MVCC**의 조합으로 결정된다.

크게 다음처럼 이해하면 좋다.

| 구성 요소               | 핵심 목적                   | 대표 키워드                                 |
| ------------------- | ----------------------- | -------------------------------------- |
| 버퍼 풀                | 데이터·인덱스 페이지 캐시 및 쓰기 버퍼링 | LRU, Free List, Flush List, Dirty Page |
| Redo Log            | 장애 후 변경 내용을 재적용해 복구     | WAL, Checkpoint, Crash Recovery        |
| Undo Log            | 롤백 및 일관된 읽기(MVCC) 제공    | 이전 버전, Read View                       |
| Doublewrite Buffer  | 페이지 일부만 기록되는 문제 방지      | Torn Page 방어                           |
| Change Buffer       | 보조 인덱스 변경을 지연 처리        | Secondary Index, Merge                 |
| Adaptive Hash Index | 자주 접근되는 패턴을 해시로 가속      | Equality Search, 자동 생성                 |
| Lock/Deadlock       | 동시 트랜잭션 간 데이터 정합성 제어    | Wait-for Graph, Deadlock Victim        |

### 1. 데드락과 자동 감지

#### 데드락이란

데드락은 둘 이상의 트랜잭션이 서로가 가진 락을 기다리면서, 누구도 진행하지 못하는 상태다.

예를 들어 다음과 같은 순서로 발생할 수 있다.

| 시점 | 트랜잭션 A              | 트랜잭션 B              |
| -- | ------------------- | ------------------- |
| 1  | `id = 1` 행 락 획득     | `id = 2` 행 락 획득     |
| 2  | `id = 2` 락을 요청하고 대기 | `id = 1` 락을 요청하고 대기 |
| 결과 | B가 가진 락을 기다림        | A가 가진 락을 기다림        |

이 경우 A와 B는 서로를 영원히 기다릴 수 있으므로, InnoDB는 데드락을 감지하면 한 트랜잭션을 강제로 롤백시켜 교착 상태를 해소한다.

#### InnoDB의 데드락 피해자 선택 기준

InnoDB는 보통 **롤백 비용이 더 적은 트랜잭션**을 데드락 피해자(victim)로 선택한다.

이때 비용은 단순히 실행 시간이 짧은 트랜잭션이 아니라, 일반적으로 다음과 같은 요소를 기반으로 판단한다.

* 변경한 행의 수
* 생성한 Undo Log의 양
* 롤백해야 하는 작업량
* 트랜잭션의 전체 작업 규모

즉, Undo Log가 적고 롤백 비용이 작은 트랜잭션이 종료 대상이 될 가능성이 높다.

이 개념은 다음처럼 설명할 수 있다.

> InnoDB는 데드락을 발견하면 전체 롤백 비용을 최소화하기 위해, 일반적으로 Undo Log가 적어 되돌리기 쉬운 트랜잭션을 피해자로 선택한다.

#### 데드락 감지 비용

InnoDB는 기본적으로 데드락 감지 기능을 활성화한다. 락 대기가 발생할 때 대기 관계를 추적하여 순환 구조가 있는지 확인한다.

하지만 매우 높은 동시성 환경에서 특정 레코드나 인덱스 범위에 락 경합이 집중되면, 데드락 탐지 자체가 큰 CPU 비용이 될 수 있다.

특히 다음 상황에서 부담이 커진다.

* 매우 많은 트랜잭션이 동일한 행 또는 인덱스 범위를 기다리는 경우
* 재고 차감, 쿠폰 발급, 인기 상품 주문처럼 핫 로우(hot row)가 존재하는 경우
* 짧은 트랜잭션이 대량으로 유입되는 경우
* 락 대기 큐가 길어지는 경우

이 경우 `innodb_deadlock_detect=OFF`를 검토할 수 있다.

다만 데드락 감지를 끄면 InnoDB가 교착 상태를 즉시 찾아내지 않는다. 교착 상태에 빠진 트랜잭션은 `innodb_lock_wait_timeout`이 만료될 때까지 대기한 뒤 락 대기 타임아웃 오류를 받는다.

| 설정          | 장점                        | 단점                       |
| ----------- | ------------------------- | ------------------------ |
| 데드락 감지 활성화  | 빠르게 데드락 해소, 불필요한 장기 대기 감소 | 대규모 락 경합에서 CPU 사용량 증가 가능 |
| 데드락 감지 비활성화 | 락 경합 상황에서 탐지 CPU 비용 감소    | 타임아웃까지 대기, 실패 요청 증가 가능   |
| 타임아웃 조정     | 최대 대기 시간 제어 가능            | 너무 짧으면 정상 트랜잭션도 실패할 수 있음 |

실무에서는 감지 기능을 바로 끄기보다 먼저 다음을 점검하는 것이 좋다.

* 트랜잭션 범위를 줄일 수 있는가
* 항상 동일한 순서로 레코드를 잠글 수 있는가
* 핫 로우를 Redis, 큐, 샤딩 등으로 분산할 수 있는가
* 하나의 트랜잭션에서 과도하게 많은 행을 변경하고 있지 않은가
* 락 획득 전에 외부 API 호출, 긴 연산, 사용자 입력 대기를 수행하고 있지 않은가

### 2. 버퍼 풀

#### 버퍼 풀이란

버퍼 풀(Buffer Pool)은 InnoDB가 디스크의 데이터 페이지와 인덱스 페이지를 메모리에 캐시하는 영역이다.

MySQL의 데이터는 테이블스페이스 파일에 저장되고, InnoDB는 일반적으로 페이지 단위로 데이터를 읽고 쓴다. 사용자가 특정 레코드를 조회하거나 변경할 때마다 디스크를 직접 읽는다면 성능이 크게 저하되므로, 자주 사용하는 페이지를 버퍼 풀에 올려두고 재사용한다.

버퍼 풀은 단순한 읽기 캐시가 아니다.

* 데이터와 인덱스 페이지를 캐시한다.
* 변경된 페이지를 메모리에 보관한다.
* 디스크 쓰기를 모아서 처리한다.
* 디스크 I/O를 평탄화한다.
* 변경된 페이지를 적절한 시점에 데이터 파일로 반영한다.

즉, 버퍼 풀은 **캐시와 쓰기 버퍼** 역할을 동시에 수행한다.

#### 버퍼 풀 크기

버퍼 풀은 일반적으로 클수록 디스크 읽기 I/O를 줄이는 데 유리하다. 다만 무조건 크게 설정하는 것은 위험하다.

버퍼 풀을 과도하게 설정하면 다음 문제가 생길 수 있다.

* MySQL 서버 프로세스의 다른 메모리 영역이 부족해질 수 있다.
* 커넥션별 버퍼와 정렬·조인·임시 테이블 메모리가 부족해질 수 있다.
* 운영체제 파일 캐시와의 메모리 경합이 발생할 수 있다.
* 메모리 부족 시 스왑이 발생하여 전체 DB 성능이 급격히 저하될 수 있다.
* 큰 버퍼 풀은 초기 적재와 관리 비용도 커질 수 있다.

따라서 버퍼 풀 크기는 단순히 “클수록 좋다”가 아니라, MySQL 전체 메모리 사용량과 동시 접속 수를 포함해 설계해야 한다.

대략적인 관점은 다음과 같다.

```
\text{총 메모리 사용량}
\approx
\text{InnoDB Buffer Pool}
+
\text{커넥션별 메모리}
+
\text{임시 테이블 메모리}
+
\text{OS 및 기타 프로세스 메모리}
```

MySQL 5.7 이후에는 버퍼 풀 크기를 동적으로 조절할 수 있으므로, 메모리 상황과 워크로드 변화에 맞추어 점진적으로 조정할 수 있다.

#### 버퍼 풀 인스턴스

큰 버퍼 풀을 하나의 전역 영역으로만 관리하면 내부 락 경합이 커질 수 있다. 이를 완화하기 위해 InnoDB는 버퍼 풀을 여러 인스턴스로 나누어 관리할 수 있다.

버퍼 풀 인스턴스는 특히 다음 환경에서 의미가 있다.

* 버퍼 풀이 매우 큰 경우
* CPU 코어 수가 많고 동시 요청량이 높은 경우
* 여러 스레드가 동시에 다양한 페이지를 읽고 쓰는 경우
* 버퍼 풀 관리 구조에서 경합이 발생하는 경우

다만 인스턴스 수를 과도하게 늘리면 각 인스턴스의 관리 효율이 떨어질 수 있으므로, 메모리 크기와 실제 경합 지표를 보고 조정해야 한다.

### 3. 버퍼 풀 내부 목록

버퍼 풀은 메모리 공간 하나만 의미하지 않는다. InnoDB는 페이지 상태와 사용 패턴을 관리하기 위해 여러 내부 리스트를 사용한다.

| 목록         | 역할                                      |
| ---------- | --------------------------------------- |
| Free List  | 아직 사용자 데이터가 적재되지 않은 빈 페이지 목록            |
| LRU List   | 자주 또는 최근 사용된 페이지를 관리하는 목록               |
| Flush List | 변경되었지만 아직 디스크 데이터 파일에 반영되지 않은 더티 페이지 목록 |

#### Free List

Free List는 버퍼 풀 안에서 아직 실제 데이터 페이지를 담고 있지 않은 빈 공간의 목록이다.

쿼리가 디스크에서 새로운 데이터 페이지를 읽어와야 할 때, InnoDB는 먼저 Free List에서 빈 페이지를 확보한다.

Free List에 빈 페이지가 없다면 InnoDB는 LRU List의 오래된 페이지를 제거(eviction)하여 공간을 만든다. 이때 제거하려는 페이지가 더티 페이지라면, 먼저 디스크에 플러시해야 할 수 있다.

즉, Free List 부족은 단순한 캐시 미스 문제가 아니라 디스크 쓰기까지 유발할 수 있다.

#### LRU List

LRU List는 디스크에서 읽어온 페이지를 가능한 오래 메모리에 유지하여, 반복적인 디스크 읽기를 줄이기 위한 구조다.

일반적인 LRU는 “가장 최근에 사용한 페이지를 앞쪽에 두고, 오래 사용하지 않은 페이지를 뒤쪽으로 보낸다”는 방식이다.

하지만 InnoDB는 단순 LRU 대신 **Young 영역과 Old 영역**을 구분한 변형 LRU 구조를 사용한다.

| 영역            | 의미                                          |
| ------------- | ------------------------------------------- |
| Young Sublist | 최근에 실제로 다시 사용된 페이지가 위치하는 영역                 |
| Old Sublist   | 처음 읽혀 들어왔거나 재사용 여부가 아직 검증되지 않은 페이지가 위치하는 영역 |

이 구조가 필요한 이유는 대량 스캔 때문이다.

예를 들어 매우 큰 테이블을 한 번만 전체 스캔하는 쿼리가 실행되면, 단순 LRU에서는 스캔된 페이지들이 기존의 자주 사용되는 캐시 페이지를 대량으로 밀어낼 수 있다. 이를 캐시 오염(cache pollution)이라고 한다.

InnoDB는 새로 읽어온 페이지를 처음부터 무조건 가장 최근 사용 영역에 넣지 않고 Old 영역에 넣는다. 이후 일정 시간 또는 접근 조건을 만족하며 다시 읽힌 페이지를 Young 영역으로 이동시킨다.

#### InnoDB에서 레코드를 찾는 과정

사용자가 특정 레코드를 조회할 때 InnoDB는 대략 다음 순서로 동작한다.

1. SQL 실행 계획에 따라 접근할 인덱스 또는 데이터 페이지를 결정한다.
2. 필요한 데이터 페이지가 버퍼 풀에 존재하는지 확인한다.
3. 버퍼 풀에 있으면 해당 페이지를 직접 읽는다.
4. 페이지가 없으면 디스크에서 필요한 페이지를 읽어 버퍼 풀에 적재한다.
5. 새 페이지는 일반적으로 LRU List의 Old 영역에 배치된다.
6. 쿼리가 페이지 내부에서 인덱스 탐색 또는 레코드 탐색을 수행한다.
7. 이후 페이지가 다시 사용되면 Young 영역으로 승격될 수 있다.
8. 오랫동안 사용되지 않은 페이지는 LRU List의 오래된 쪽으로 이동한다.
9. 새 공간이 필요하면 오래 사용되지 않은 페이지가 우선적으로 제거 대상이 된다.

정리하면 다음과 같다.

> InnoDB는 레코드 자체가 아니라 페이지 단위로 데이터를 버퍼 풀에 적재한다. 따라서 하나의 레코드를 조회하더라도 해당 레코드가 포함된 데이터 페이지 또는 인덱스 페이지 전체가 메모리에 올라온다.

### 4. Flush List와 더티 페이지

#### 더티 페이지란

버퍼 풀에 존재하는 페이지가 UPDATE, INSERT, DELETE 등에 의해 변경되면 그 페이지는 디스크의 데이터 파일과 메모리 내용이 달라진다.

이처럼 메모리에서는 변경되었지만 아직 데이터 파일에 반영되지 않은 페이지를 **더티 페이지(Dirty Page)** 라고 한다.

더티 페이지는 버퍼 풀에 계속 남아 있을 수 있고, 일정 조건이 되면 디스크의 실제 데이터 파일로 기록된다.

#### Flush List의 역할

Flush List는 더티 페이지를 관리하는 목록이다.

페이지가 처음 변경될 때 InnoDB는 해당 페이지를 Flush List에 추가한다. Flush List는 단순히 최근 변경 순서만 기록하는 용도보다, **Redo Log와 데이터 페이지의 동기화 관계를 관리하는 용도**로 이해하는 것이 중요하다.

각 더티 페이지는 최초 변경 시점과 관련된 LSN(Log Sequence Number)을 가진다. InnoDB는 이 정보를 바탕으로 어떤 더티 페이지를 먼저 디스크에 기록해야 하는지 판단한다.

#### 버퍼 풀 플러시의 목적

버퍼 풀 플러시는 “메모리를 청소하는 작업” 정도로 이해하면 부족하다. 실제로는 다음 목적을 함께 가진다.

* Redo Log 공간을 재사용할 수 있도록 체크포인트를 전진한다.
* Free List에 사용할 여유 페이지를 확보한다.
* 더티 페이지 비율이 지나치게 높아지는 것을 방지한다.
* 쓰기 I/O가 특정 순간에 몰리지 않도록 평탄화한다.
* 장애 복구 시 Redo Log를 재적용해야 하는 범위를 줄인다.

따라서 플러시는 성능 저하를 만드는 불필요한 작업이 아니라, 안정적인 쓰기 처리량과 복구 가능성을 유지하는 핵심 작업이다.

***

### 5. Redo Log와 체크포인트

#### Redo Log의 목적

Redo Log는 데이터 변경 사실을 기록하는 로그다. 서버가 비정상 종료되더라도, 데이터 파일에 아직 반영되지 않은 변경 내용을 다시 적용하여 복구할 수 있게 한다.

핵심 원칙은 WAL(Write-Ahead Logging)이다.

> 데이터 파일을 디스크에 기록하기 전에, 변경 내용을 먼저 Redo Log에 안전하게 기록한다.

예를 들어 사용자가 주문 상태를 `PAYMENT_COMPLETED`로 변경했다고 하자.

1. 버퍼 풀의 해당 데이터 페이지가 변경된다.
2. 변경 내용에 대한 Redo Log가 기록된다.
3. 커밋 시점에는 Redo Log의 내구성이 우선 보장된다.
4. 실제 테이블 데이터 파일 반영은 이후 플러시 과정에서 수행될 수 있다.

이 구조 덕분에 매 트랜잭션마다 테이블 데이터 파일을 즉시 기록하지 않고도 내구성을 유지할 수 있다.

#### Redo Log 파일 구조

Redo Log는 고정 크기의 로그 파일들을 순환 구조로 사용한다. 로그는 계속 기록되지만, 사용 가능한 공간이 필요하므로 이전 로그 영역은 무한히 보존될 수 없다.

오래된 Redo Log 영역을 재사용하려면, 그 로그가 가리키는 더티 페이지가 먼저 데이터 파일에 기록되어야 한다.

즉, 다음 관계가 성립한다.

```
\text{Redo Log 재사용}
\Rightarrow
\text{관련 Dirty Page 플러시}
\Rightarrow
\text{Checkpoint 전진}
```

Redo Log가 너무 작으면 자주 체크포인트가 발생하고, 더티 페이지 플러시가 빈번해져 쓰기 성능이 떨어질 수 있다.

반대로 Redo Log가 너무 크면 쓰기 버퍼링과 처리량에는 유리할 수 있지만, 장애 발생 시 복구해야 하는 로그 범위가 커질 수 있다.

#### 버퍼 풀과 Redo Log 크기 관계

버퍼 풀이 클수록 메모리에 더 많은 더티 페이지를 유지할 수 있다. 하지만 Redo Log 공간이 작다면 많은 더티 페이지를 메모리에 오래 쌓아둘 수 없다.

Redo Log 공간이 부족해지면 InnoDB는 체크포인트를 빠르게 전진시키기 위해 더티 페이지를 적극적으로 플러시해야 한다. 이 과정에서 쓰기 I/O가 증가하고, 갑작스러운 성능 저하가 발생할 수 있다.

따라서 쓰기 비중이 높은 시스템에서는 다음을 함께 봐야 한다.

* 버퍼 풀 크기
* Redo Log 전체 용량
* 체크포인트 발생 빈도
* 더티 페이지 비율
* 스토리지의 지속 쓰기 처리량
* 장애 복구 허용 시간(RTO)

메모의 “버퍼 풀 100GB라면 Redo Log 총량을 5\~10GB 수준으로 고려” 같은 값은 출발점으로 참고할 수 있지만, 고정된 정답은 아니다. 실제 워크로드와 복구 시간 목표를 기준으로 조정해야 한다.

#### 더티 페이지 비율

더티 페이지 비율은 버퍼 풀 전체 페이지 중 아직 디스크에 반영되지 않은 페이지의 비중이다.

```
\text{Dirty Page Ratio}
=
\frac{\text{Dirty Pages}}{\text{Total Buffer Pool Pages}}
\times 100
```

더티 페이지 비율이 너무 높으면 다음 문제가 생길 수 있다.

* Free List가 부족해질 수 있다.
* 페이지 교체 시 즉시 플러시가 필요해질 수 있다.
* 체크포인트 압박이 커질 수 있다.
* 순간적인 디스크 쓰기 폭증이 발생할 수 있다.
* 쿼리 지연 시간이 불안정해질 수 있다.

반대로 지나치게 낮게 유지하면 더 자주 디스크에 기록하므로, 쓰기 병합 효과를 충분히 활용하지 못할 수 있다.

***

### 6. Doublewrite Buffer

#### 필요한 이유: Torn Page

스토리지 장치나 운영체제는 데이터 페이지 전체를 원자적으로 기록하지 못할 수 있다. 예를 들어 16KB 페이지를 쓰는 도중 서버가 비정상 종료되면, 페이지의 앞부분만 새 데이터로 기록되고 뒷부분은 이전 데이터로 남는 문제가 발생할 수 있다.

이를 Torn Page 또는 Partial Page Write라고 한다.

Redo Log만으로는 손상된 데이터 페이지를 항상 안전하게 복구할 수 없다. Redo Log는 특정 페이지를 다시 적용할 수 있지만, 기반 페이지 자체가 깨졌다면 복구 과정이 복잡하거나 불가능할 수 있기 때문이다.

#### Doublewrite Buffer 동작

Doublewrite Buffer는 데이터 파일에 더티 페이지를 기록하기 전에, 먼저 별도의 임시 영역에 페이지를 기록하는 방식이다.

대략적인 흐름은 다음과 같다.

1. 버퍼 풀의 더티 페이지를 모은다.
2. 해당 페이지를 Doublewrite Buffer 영역에 먼저 기록한다.
3. Doublewrite Buffer 기록이 완료되면 실제 테이블스페이스 데이터 파일에 기록한다.
4. 서버 장애로 데이터 파일 페이지가 일부만 기록되었다면, Doublewrite Buffer의 정상 페이지를 사용해 복구한다.

즉, Doublewrite Buffer는 평상시에 읽기 성능을 높이는 기능이 아니라, 비정상 종료나 부분 페이지 기록 문제로부터 데이터 페이지의 일관성을 보호하는 안정성 장치다.

***

### 7. Undo Log와 MVCC

#### Undo Log의 목적

Undo Log는 데이터 변경 이전의 값을 저장하는 로그다.

Redo Log가 “장애가 나면 변경 내용을 다시 적용하기 위한 로그”라면, Undo Log는 “변경을 되돌리고 이전 버전을 보여주기 위한 로그”다.

| 구분      | Redo Log                   | Undo Log                  |
| ------- | -------------------------- | ------------------------- |
| 핵심 목적   | 장애 복구                      | 롤백 및 MVCC                 |
| 기록 내용   | 변경 내용을 재적용할 정보             | 변경 이전 값                   |
| 장애 발생 시 | 변경 내용을 다시 적용               | 미완료 트랜잭션 변경을 되돌림          |
| 주 사용 시점 | Crash Recovery, Checkpoint | Rollback, Consistent Read |
| 데이터 관점  | 앞으로 다시 수행                  | 과거 상태로 되돌림                |

#### 트랜잭션 롤백

트랜잭션이 실패하거나 명시적으로 `ROLLBACK`되면, InnoDB는 Undo Log를 사용하여 변경 이전 값으로 데이터를 복원한다.

예를 들어 재고를 100에서 99로 차감한 뒤 결제 처리에서 오류가 발생했다면, 트랜잭션 롤백 시 Undo Log를 이용해 재고 값을 다시 100으로 복구할 수 있다.

#### 격리 수준과 일관된 읽기

Undo Log는 MVCC(Multi-Version Concurrency Control)의 핵심 구성 요소다.

한 트랜잭션이 데이터를 변경하는 동안, 다른 트랜잭션이 그 변경 내용을 즉시 봐야 하는 것은 아니다. 격리 수준과 Read View에 따라 다른 트랜잭션은 변경 전 버전을 읽어야 할 수 있다.

예를 들어 다음 상황을 생각할 수 있다.

| 트랜잭션 A                        | 트랜잭션 B                            |
| ----------------------------- | --------------------------------- |
| 상품 가격을 10,000원 → 12,000원으로 변경 | 기존 시점 기준으로 가격 조회                  |
| 아직 커밋하지 않음                    | Undo Log의 이전 버전인 10,000원을 읽을 수 있음 |

즉, Undo Log는 단순히 롤백을 위한 데이터가 아니라, 다른 트랜잭션에 일관된 스냅샷을 제공하기 위한 이전 버전 저장소 역할도 한다.

#### 장기 트랜잭션의 위험

오래 실행되는 트랜잭션은 Undo Log 정리를 지연시킨다.

InnoDB는 더 이상 어떤 트랜잭션도 필요로 하지 않는 Undo Log만 제거할 수 있다. 그런데 오래된 Read View를 가진 트랜잭션이 계속 살아 있으면, 그 트랜잭션이 과거 버전을 읽을 가능성이 있으므로 관련 Undo Log를 제거할 수 없다.

그 결과 다음 문제가 생길 수 있다.

* Undo Log 및 History List Length 증가
* Undo 테이블스페이스 사용량 증가
* Purge 작업 지연
* 오래된 버전 탐색 비용 증가
* 일반 조회 성능 저하
* 디스크 공간 증가
* 복제 지연 또는 운영 불안정성 증가 가능성

중요한 것은 Undo Log 공간 자체보다, 오래된 버전을 따라가며 읽어야 하는 **MVCC 버전 체인 탐색 비용**이 쿼리 성능에 영향을 줄 수 있다는 점이다.

실무적으로는 다음을 점검한다.

* 장시간 열린 트랜잭션이 있는지
* `Sleep` 상태지만 트랜잭션이 종료되지 않은 커넥션이 있는지
* 배치 작업이 대량 변경을 하나의 긴 트랜잭션으로 묶고 있지 않은지
* 애플리케이션에서 예외 발생 후 롤백 또는 커넥션 반환이 누락되지 않는지
* History List Length가 계속 증가하는지

### 8. Change Buffer

#### Change Buffer란

INSERT, UPDATE, DELETE가 발생하면 클러스터드 인덱스뿐 아니라 보조 인덱스(secondary index)도 함께 갱신해야 한다.

문제는 변경해야 할 보조 인덱스 페이지가 버퍼 풀에 없을 수 있다는 점이다. 이때 매번 해당 인덱스 페이지를 디스크에서 읽어와 갱신하면 랜덤 디스크 I/O가 늘어난다.

Change Buffer는 버퍼 풀에 없는 보조 인덱스 페이지의 변경 작업을 즉시 디스크 페이지에 반영하지 않고, 별도 공간에 임시로 저장해 두었다가 나중에 병합(merge)하는 기능이다.

흐름은 다음과 같다.

1. 보조 인덱스 변경이 필요하다.
2. 대상 인덱스 페이지가 버퍼 풀에 없다.
3. 디스크에서 인덱스 페이지를 즉시 읽지 않는다.
4. 변경 내용을 Change Buffer에 기록한다.
5. 이후 해당 인덱스 페이지가 버퍼 풀로 읽히거나 백그라운드 작업이 수행될 때 변경 내용을 병합한다.

이 방식은 특히 디스크 랜덤 I/O가 비싸고, 보조 인덱스 변경이 빈번한 워크로드에서 도움이 될 수 있다.

#### 유니크 인덱스에 적용하기 어려운 이유

유니크 인덱스는 INSERT 또는 UPDATE 시 중복 여부를 즉시 확인해야 한다.

대상 인덱스 페이지를 읽지 않고 변경만 임시 저장하면, 이미 같은 값이 존재하는지 정확히 판단할 수 없다. 따라서 유니크 보조 인덱스에는 Change Buffer를 사용할 수 없다.

| 인덱스 유형     | Change Buffer 사용 |
| ---------- | ---------------- |
| 일반 보조 인덱스  | 가능               |
| 유니크 보조 인덱스 | 불가               |
| 클러스터드 인덱스  | 일반적으로 대상 아님      |

#### Change Buffer 크기

Change Buffer는 버퍼 풀의 일부 공간을 사용한다. 너무 크게 잡으면 실제 데이터·인덱스 페이지를 캐시할 공간이 줄어들 수 있다.

따라서 쓰기 지연 효과와 버퍼 풀 캐시 효율 사이의 균형이 필요하다. 실무에서는 대량 쓰기와 보조 인덱스가 많은 테이블에서 효과를 확인하되, SSD 환경에서는 과거 HDD 환경만큼의 이점이 크지 않을 수 있다.

***

### 9. Adaptive Hash Index

#### Adaptive Hash Index란

Adaptive Hash Index(AHI)는 InnoDB가 내부적으로 자주 접근되는 B+Tree 인덱스 탐색 패턴을 감지하여, 일부 인덱스 경로에 대해 해시 기반 접근 구조를 자동으로 만드는 기능이다.

B+Tree 인덱스는 범위 검색, 정렬, 순차 접근에 강점이 있다. 반면 해시 인덱스는 일반적으로 동등 조건 검색에 강점이 있다.

AHI는 B+Tree를 완전히 대체하는 별도 사용자 인덱스가 아니다. InnoDB가 관찰한 접근 패턴을 바탕으로 내부적으로 최적화하는 보조 구조다.

#### B+Tree와 AHI의 차이

| 항목    | B+Tree 인덱스       | Adaptive Hash Index  |
| ----- | ---------------- | -------------------- |
| 생성 주체 | 사용자가 DDL로 생성     | InnoDB가 자동 생성·관리     |
| 저장 대상 | 테이블 또는 인덱스 구조    | 버퍼 풀의 자주 접근되는 페이지 기반 |
| 주 용도  | 동등 조건, 범위 조건, 정렬 | 반복적인 동등 조건 접근        |
| 범위 검색 | 유리               | 부적합                  |
| 유지 비용 | DML에 따른 인덱스 갱신   | 해시 구조 생성·경합·유지 비용    |
| 영속성   | 디스크에 영속          | 메모리 기반, 재시작 시 재생성    |

#### AHI가 유리한 상황

다음과 같은 조건에서 AHI가 도움이 될 수 있다.

* 반복적으로 동일하거나 유사한 동등 조건 검색이 발생하는 경우
* 특정 키 또는 일부 데이터에 접근이 집중되는 경우
* 조회 대상 페이지가 이미 버퍼 풀에 충분히 올라와 있는 경우
* 매우 큰 테이블에서 특정 레코드를 반복 조회하는 경우
* B+Tree 탐색 경로를 반복적으로 타는 경우

예를 들면 다음과 같은 패턴이다.

```
SELECT *
FROM order_item
WHERE order_id = ?;
```

특정 주문 ID 또는 특정 키 범위가 반복적으로 조회되고 관련 페이지가 버퍼 풀에 존재한다면 AHI가 탐색 비용을 줄이는 데 도움을 줄 수 있다.

#### AHI가 불리한 상황

AHI는 자동 최적화 기능이지만 항상 이득이 되는 것은 아니다.

다음과 같은 상황에서는 유지 비용이나 내부 경합이 더 커질 수 있다.

* 범위 조건 검색이 많은 경우
* 대량 스캔이 많은 경우
* 데이터 접근 분포가 넓고 특정 패턴에 집중되지 않는 경우
* 쓰기 비중이 매우 높은 경우
* AHI 관련 내부 락 또는 경합이 두드러지는 경우
* 버퍼 풀 적중률이 낮아 디스크 읽기가 대부분인 경우

따라서 AHI는 “켜면 무조건 빨라지는 기능”이 아니라, 실제 워크로드와 모니터링 지표를 보고 활성화 여부를 판단해야 한다.

***

### 10. 면접용 핵심 요약

#### 버퍼 풀

> 버퍼 풀은 InnoDB가 데이터와 인덱스 페이지를 메모리에 캐시하고, 변경된 페이지를 모아서 디스크에 기록하는 공간입니다. 따라서 읽기 캐시뿐 아니라 쓰기 버퍼링, 디스크 I/O 평탄화, 더티 페이지 관리까지 담당합니다.

#### Redo Log

> Redo Log는 장애가 발생했을 때 커밋된 변경 내용을 재적용하기 위한 로그입니다. 데이터 파일보다 먼저 기록하는 WAL 방식을 사용하기 때문에, 매 변경마다 데이터 페이지를 즉시 디스크에 쓰지 않아도 내구성을 보장할 수 있습니다.

#### Undo Log

> Undo Log는 변경 전 데이터를 보관해 롤백을 가능하게 하고, MVCC 기반의 일관된 읽기를 제공합니다. 장기 트랜잭션이 유지되면 과거 버전을 제거하지 못해 Undo Log와 버전 체인이 누적되고, 결국 조회 성능과 시스템 전반에 영향을 줄 수 있습니다.

#### 데드락

> InnoDB는 락 대기 관계에서 순환이 발생하면 데드락으로 판단하고, 일반적으로 롤백 비용이 작은 트랜잭션을 종료해 교착 상태를 해소합니다. 다만 고경합 환경에서는 데드락 감지 자체가 CPU 병목이 될 수 있어, 요청 직렬화나 타임아웃 기반 제어를 함께 검토해야 합니다.

#### Change Buffer

> Change Buffer는 버퍼 풀에 없는 일반 보조 인덱스 페이지를 즉시 디스크에서 읽어 수정하지 않고, 변경 내용을 임시 저장한 뒤 나중에 병합하는 기능입니다. 유니크 인덱스는 중복 검사가 즉시 필요하므로 적용할 수 없습니다.

#### Doublewrite Buffer

> Doublewrite Buffer는 더티 페이지를 실제 데이터 파일에 쓰기 전에 별도 영역에 한 번 더 기록해, 장애 중 페이지 일부만 기록되는 Torn Page 문제를 방어하는 안전장치입니다.

#### AHI

> Adaptive Hash Index는 InnoDB가 반복적인 동등 조건 검색 패턴을 감지해 B+Tree 탐색을 해시 접근으로 가속하는 내부 구조입니다. 다만 쓰기 경합이나 유지 비용이 커질 수 있으므로, 실제 워크로드를 기준으로 활성화 여부를 판단해야 합니다.
