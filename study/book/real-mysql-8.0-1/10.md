# 10장 실행계획

옵티마이저는 항상 좋은 실행계획을 세우지 않는다.&#x20;



디비가 보여주는 실행계획을 읽는 순서 , 출력하는 키워드 , 그리고 알고리즘에 대해 살펴보는 정도



* 통계 정보 , 데이터 분포도를 수집해서 저장하는 히스토그램 정보가 도입
* 테이블 및 인덱스 통계 정보 : mysql 은 비용기반 최적화를 사용하지만 , 통계 정보의 정확도가 높지 않고 통계 정보의 휘발성이 강하다.&#x20;
* 통계 정보들을 영구적으로 관리할수있게 개선 , 재시작 되도 유지될수있도록 (설정 값 저장 가능)
* inno\_db\_table\_stat :&#x20;

갱신하는 기준은 다음과 같다&#x20;

* 테이블 오픈 경우 , 레코드가 대량 갱신 경우 (전체 레코드가 1/16 정도 update 또는 insert 를 해줄셩우)
* analyze 실행하는 경우

더 정확한 통계 정보를 수집하기 위해 다양한 설정값을 적용이 가능하겠지만, 이것들로 인한 정보 수집 시간이 길어지게 될수있므로 주의&#x20;



히스토그램 이란...

칼럼의 데이터 분포도를 참조할수있는 정보를 히스토그램 정보이다. 예전에는 인덱스 칼럼의 유니크한 값의 갯수 정도만 가지고 있기 떄문에 말이다.&#x20;

두가지를 지원한다&#x20;

* 싱글톤 : 칼럼값 개별로 레코드 건수 관리
* 높이 균형 : 칼럼값의 범위를 균등한 갯수로 구분해서 관리하는 히스토그램

유니크한 값의 갯수가 적으면 싱글톤,&#x20;

이걸 어따 써먹냐 ,,

이게 있고 없고 차이로 어떤 데이터 유형의 분포도가 높아지는가 .. .





히스토그램과 인덱스

조건절에 일치하는 레코드 건수를 예측하기 위해 옵티마이저는 샘플링을 해서 살펴 보는데 이걸 인덱스 다이브라고 표현



실행계획 분석

사실 이게 가장 중요하다.&#x20;





#### id 칼럼&#x20;

실행 계획을 하는 단위 select 쿼리별로 부여되는 식별자 값

단 여러 테이블 조인하면 id 를 같이 가진다.&#x20;

id 칼럼이 테이블의 접근 순서를 의미하지는 않는다.&#x20;



#### select\_type 칼럼

어떤 타입의 쿼리인지가 표시되는&#x20;

* simple : union subQuery 등 단순한 쿼리 일경우
* primary : union subQuery 가진 쿼리에서 가장 바깥쪽 에 있는 단위 쿼리
* union : 첫번째 인자 이후에 두번째 단위 부터 셀렉트 쿼리 , 첫번째 인자 이후에 는 임시 테이블(DERIVED)이 select \_type 로 표시
* DEPENDENT UNION : union and union all 로 집합을 결합하는 쿼리에 표시
* union RESULT : union 결과를 담아주는 테이블 의미 , 8 이전에는 임시테이블로 만들었는데, union all 에서는 임시테이블 없이 개선이 됐는데 , union  은 임시 테이블이 그대로다&#x20;
* subquery : 여러가지가 있다 \
  중첩 쿼리 : select 칼럼에 적용된 서브쿼리\
  서브쿼리 : 일반적인 where 절에 발생되는 서브 쿼리\
  파생 테이블 : from 절에서 사용되는 서브쿼리
* DEPENDENT SUBQUERY : ㄱ바깥쪽 select 쿼리에 정의된 칼럼을 사용하는 경우
* DERIVED.: 단위 select 쿼리의 실행결과로 메모리나 디스크에 임시 테이블에 생성하는걸로 의미 이전에는 파생테이블에 인덱스가 없어서 성능상 문제가 되었지만 5.6 버전 부터는 옵티마이저 옵션에 따라 쿼리의 특성에 맞게 인덱스를 추가해서 만들수있게 처리&#x20;
* uncacheable. subquery : 서브쿼리의 실행결과를 사용할수있게 결과를 내부적인 캐시공간으로 담아둔다. 이걸 사용할수있나 없는 차이점



#### table 칼럼 :&#x20;

없는 테이블을 조회할때 오라클은 오류를 발생하지만 mysql 은 있는것처럼 작동은 한다.&#x20;

테이블을 사용하지 않는 쿼리인 경우엔 table 은 null 로 나올거다 .&#x20;



#### partitions 칼럼

파티션 관련 실행 계획까지 모두 확인 할수있게 변경 되었다.&#x20;

파티션이 여러 개인 테이블에서 불필요한 파티션을 빼고 접근이 필요할거같은 테이블만 골라내는 과정을 파티션 프루닝 이라 한다. 만약 파티셔닝 type 칼럼 값이 all 이다. 이럴떄는 독립적인 파티션 내부에서 풀스캔을 뜬다.&#x20;





#### type 칼럼

레코드를 어떤 방식으로 읽는지 나타낸다.&#x20;

all 를 제외한 나머지는 모두 인덱스를 사용하는 접근 방법이다.

* system : 1건 또는 한건도 존재하는 테이블을 참조하는 형태의 접근 방법 (inno db 에서 사용 x )
* const : 기본 키 또는 유니크 키 칼럼을 이용하는 조건절을 이용해 1건을 반환 쿼리의 처리 방식을&#x20;
* eq\_ref : 여러 테이블이 조인되는 쿼리의 실행 계획에서만 표시 두번째 이후에 읽는 테이블에서 1건만 존재했을떄 보장이 있어야 사용하는 접근법 , 조인에서 첫번째 읽은 테이블의 칼럼값을 이용해 두번째 테이블을 프라이머리 키나 유니크 키로 동등 조건
* ref : 조인의 순서와 관계없이 사용 , 인덱스 종류와 상관없이 동등조건 검색할때 접근방법&#x20;
* fulltext : 전문 검색 인덱스를 사용해 레코드를 읽는 접근 방법, 우선 순위 가 높다. 위 세개 아니면 바로 이걸로 비빈다.&#x20;
* ref\_or\_null : null 비교 추가&#x20;
* unique\_subquery : in 서브쿼리 를 위한 접근 , 중복되지 안흥ㄴ 유니크 한 값만 반환 &#x20;
* range. : 인덱스 레인지 스캔 형태의 접근 방법 (이것만 나오면 ㅅㅌㅊ 방법)
* index\_merge : 2개이상 인덱스를 이용해 만들고 병합하는 방법 \
  여러 인덱스 읽어야 해서 range 보다는 비효율적 \
  전문 검색 할때는 안됨 \
  2개 이상 작업이 되기 때문에 교집합 합집합 또는 중복 제거 같은 부가 작업이 필요하다.&#x20;
* index : 인덱스 풀 스캔 의미&#x20;

#### extra 칼럼 (중요하다  )

**Using where**

* 읽어온 레코드에 조건을 적용해서, 다음 조인으로 넘기거나 결과로 반환할 레코드를 걸러낸다는 의미.
* 인덱스를 사용하지 않았다는 뜻은 아니다. `type = range`나 `ref`와 함께 나올 수 있다.
*   중요한 건 이 문구 자체보다, 접근 과정에서 읽는 행 수와 조건을 통과하는 행 수의 차이다.[mysql](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html)

    > 한 줄 정리: 읽은 데이터에 조건을 적용한다. 많이 읽고 대부분 버리는지가 중요하다.



**Using index**

* 조회에 필요한 칼럼을 인덱스에서 얻을 수 있다는 의미.
* 일반적인 보조 인덱스 조회처럼 실제 데이터 레코드를 추가로 찾는 작업을 피하는 커버링 인덱스 방식.
* `type = index`와는 다르다. `type = index`는 인덱스 전체 스캔이고, `Extra = Using index`는 필요한 정보를 인덱스로 충족한다는 뜻이다.
* 따라서 `Using index`가 나와도 수억 개의 인덱스 엔트리를 읽으면 느릴 수 있다.

> 한 줄 정리: 데이터 레코드 추가 조회를 줄인다. 읽는 인덱스 엔트리 수까지 줄여주는 것은 아니다.

**Using index condition**

* ICP, Index Condition Pushdown이 적용된다는 의미.
* 인덱스에 포함된 칼럼의 조건을 먼저 평가하고, 조건을 통과하는 경우에만 실제 데이터 레코드를 읽는다.
* 인덱스로 접근하는 범위 자체를 줄이는 것과, 그 범위 안에서 데이터 레코드 조회를 줄이는 것을 구분해야 한다.
* `Using index`처럼 인덱스만으로 조회가 끝난다는 뜻은 아니다.[mysql](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html)

> 한 줄 정리: 인덱스에서 먼저 걸러서, 불필요한 데이터 레코드 조회를 줄인다

**Using filesort**

* 인덱스 순서만으로 필요한 정렬을 해결하지 못해 별도의 정렬 작업을 수행한다는 의미.
* 이름에 `file`이 있어도 반드시 디스크에서 정렬한다는 뜻은 아니다. 메모리 또는 디스크를 사용할 수 있다.
*   정렬 대상이 몇 건인지가 중요하다. 100건 정렬과 1,000만 건 정렬은 같은 문구여도 비용이 다르다.mysql+1

    > 한 줄 정리: 별도 정렬이 필요하다. 디스크 정렬 여부보다 먼저 정렬 입력 건수를 본다.

**Using temporary**

* 쿼리 처리를 위해 내부 임시 테이블이 필요하다는 의미.
* 그룹화·중복 제거 등 중간 결과를 보관하는 과정에서 나타날 수 있다.
* 특히 `GROUP BY`와 `ORDER BY`가 서로 다른 칼럼 구성을 사용할 때 발생할 수 있다.
*   이 문구만으로 임시 테이블의 크기나 실제 디스크 사용 여부를 확정할 수는 없다.[mysql](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html)

    > 한 줄 정리: 중간 결과를 임시 테이블에 담는다. 얼마나 큰 중간 결과를 만드는지가 중요하다.
