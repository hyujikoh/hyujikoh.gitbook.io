# 가비지 컬렉터와 메모리 할당 전략

어떤 메모리를 회수 하나 , 언제 회수 하고 , 어떻게 회수 해야 할까 이게 제일 중요하다 .&#x20;

대상이 죽었는지 확인을 해야 그래야 수집하고 버릴수있다.&#x20;

수집하고 참조하는 객체가 없는 즉 카운팅이 없으면 그 객체는 사용할수없다



자바에서 GC 루트로 할수있는 객체&#x20;

* 가상 머신 스택에서 참조하는 객체 : 현재 실행중인 메서드에 매개변수 지역 변수 임시 변소
* 메서드 영역에서 클래스가 정적 필드로 참조하는 객체
* 메서드 영역에서 상수로 참조되는 객체
* JNI 가 참조하는 객체 , class 객체 , 동기화로 잠겨있는 모든 객체&#x20;





| 종류      | 선언/클래스                | GC 회수 기준                      | 대표 용도                       | 핵심                |
| ------- | --------------------- | ----------------------------- | --------------------------- | ----------------- |
| 강한 참조   | 일반 변수 참조              | 강한 참조가 하나라도 있으면 회수하지 않음       | 일반적인 모든 객체 사용               | 기본 참조             |
| 부드러운 참조 | `SoftReference<T>`    | 메모리가 부족할 때 GC가 회수 가능          | 메모리 민감 캐시                   | “메모리 여유 있으면 유지”   |
| 약한 참조   | `WeakReference<T>`    | 강한/부드러운 참조가 없으면 다음 GC에서 회수 가능 | `WeakHashMap`, 리스너/메타데이터 연결 | “GC가 돌면 사라질 수 있음” |
| 유령 참조   | `PhantomReference<T>` | 객체 회수 직전/후처리 시점 감지용           | 네이티브 리소스 정리, 생명주기 추적        | 객체 접근 불가, 알림만 받음  |





### 가비지 컬렉팅 알고리즘

마크 스윕 : \
회수할 객체를 표시하고 컬렉팅 따로 작업 한게 없고 그나마 바로 진행하고 구현한다. \
단점 : 실행 효율이 일정 치 않고 , 메모리 파편화가 심하다\
\
마크 카피 알고리즘 \
회수할 객체가 많아지면 효율이 떨어지는 위 알고리즘을 해결하기 위해 가용 메모리를 반갈 해서 한쪽만 사용하다 이제 컬력팅 하면 살아남은 객체는 다른 블록에 복사하고 기존 블록을 한번에 청소한다. 대다수의 객체가 회수 된다면 효율이 죽인다. 단 가용 메모리는 절반밖에 못쓴다는 단점이 있다.&#x20;

마크 컴팩트 알고리즘 : \
표시 단계는 마크 스윔과 동일하지만 컴팩트 단계에서 모든 객체 메모리 영역의 한쪽 끝을 모은다음 나머지 공간을 한번에 비운다. 큰 차이는 메모리 이동이 일어난다는 것이다. 단 이 문제에서 살아남은 객체의 참조가 이동되어서 모두 갱신을 해야한다는 점이다. 이동 시키지 않는다면 할당이 빡세고 이동 시키면 회수 작업이 복잡해진다. <br>



### 클래식 가비지 컬렉션

CMS 와 G1 은 그나마 자세히 보는듯 ?&#x20;

단 여기서 명시하는건 어떤 시나리오에 GC 가 가장 적합한지를 선택할수있는 수준의 요약만 필요하다.&#x20;

#### 시리얼

단일 스레드로 동작 , 무엇보다 GC 가 시작되면 회수가 완료 될때까지 모든 작업 스레드 멈춰야 한다. 다만 가장 간단하교 효율적이라는 이점이 있다. 알고리즘 에서 요구하는 메모리 사용량이 적다. 스레드 상호 작용에 의한 오버 해드가 없다 .&#x20;

신세대 : 마크 카피 , 구세대 : 마크 컴팩트&#x20;



병렬과 동시성의 차이&#x20;

병렬 : GC 스레드 다수가 동시에 함께 작업을 수행

동시 : GC 스레드와 사용자 스레드가 동시에 일을 진행한다는&#x20;



#### CMS&#x20;

표시와 쓸기를 동시에 수행 , 이 GC 의 철학은 GC 로 인한 일시 정지 시간을 최소로 줄이는 것이 목표다 . 서비스 응답시간이 중요하다고 하면 이게 더 중요하지 않을까 싶다.&#x20;

1. 최초 표시 : GC 루트와 직접 연결된 객체들만 표기&#x20;
2. 동시 표시 : 객체 그래프로 전체 탐색 , 사용자 스레드가 멈추지는 않지만 오래걸린다.
3. 재표시 : 탐색 중 사용자 스레드가 참조 관계를 변경한 객체들을 바로 잡는다. 일시정지 시간은 최조보다는 길다.
4. 동시 쓸기 : 죽었다고 판단 되는 애들은 전부 다이&#x20;

다만 단점 존재&#x20;

1. 프로세서 자원에 아주 민감하다. 같이 공유하고 동시에 하기 때문에 말이다.&#x20;
2. 부유 쓰레기 를 처리하지 못해서 동시 모드 실패를 유발 가능성 존재 . 그러다 full gc 때린다.&#x20;
3. CMS 의 토대는 마크 스윕 알고리즘이다. 그래서 전체 GC 를 해서 객체 공간을 확보할수가 있다. 다만 이런걸 방지하기 위해 조각 모음 수행하는 스위치가 존재한다.&#x20;



#### G1

서버용 어플리케이션에 집중한 컬렉터. 정지시간 예측 모델을 만들고자 한다. 목표 시간을 설정하면 가비지 컬렉터가 쓰는 시간이 밀리초를 넘지 않도록 통제 하는 거는것이다 .&#x20;

즉 내가 지정한 시간 범위에 GC 처리를 하는것이 목표이자 철학이다.&#x20;

여기서 기존 매커니즘과 다르게 어느 영역에 쓰레기가 가장 많고 가성비 이득이 좋은건가 판단을 한다. 회수 집합 (cset)

각 리전은 필요에 따라 신세대 에덴 , 생존자 , 구세대 공간 등등이 일어날수있다.

다만 리전을 넘는 큰 객체 거대리전을 통해서 gc 쳐서 구세대로 치긴 한다.&#x20;

이걸 해결 하기 위해 G1 이 해결하는 문제

1. 객체의 리전간 참조 문제 = 기억집합을 도입하여 GC 루트부터 힙 전체를 스캔하는 일 지양 기억 집합은 기본적으로 해시테이블 구조 , 내가 가리키는 대상 과 나를 가르키는 대상 구조로 기록 이떄문에 자바 힙을 최소 10\~20% 사용
2. 동시 표시 기간 동안 각각 다른 스레드가 간섭하지 않도록 보장 , 이를 위해 객체 그래프 구조 파괴 하지 않도록 보장 필요 = 스냅숏 알고리즘 , TAMS 두 포인터 로 설계 해서 해결&#x20;
3. 신뢰할수 있는 정지 예측 모덜 구현



GC 처리 순서&#x20;

1. 최초 표시 : GC 루트 직접 참조하는 객체들 표시하고, TAMS 포인터 값 수정 , 스냅숏 생성 , 일시 정지 시간 매우 짧음 사용자 스레드 일시 정지&#x20;
2. 동시 표시 : 루트로 시작된 객체 도달 가능성 분석 하여 회수할 객체 찾는다 . 시간 걸리지만 사용자 스레드와 동시 수행 되기 때문에 ㄱㅊ , 스냅숏 과 비교하여 참조 변경 객체 다시 스켄
3. 재표시 : 다시 사용자 스레드 멈추는 ㄱ단계 , 스냅숏 이후 변경된 소수의 객체만 처리하면 되므로&#x20;
4. 통계 데이터를 기초로 리전의 비용과 적절한 계획을 세우고 , 지운다 . 이때 살아남은 객체는 이동시킨다 . 그때 사용자 스레드가 멈추긴 한데 다수 GC 스레드가 병렬로 처리한다.&#x20;

다시한번 이야기 하지만 공식 목표는 지연시간 제어 동시에 가장 처리량 높이는것이 목표다 .&#x20;
