# 9장 실행계획

사용자의 요청을 처리 하기 위한 최적의 비용을 뽑아내는것이 목표



#### 실행 절차&#x20;

1. db 가 이해할수있도록 sql 쪼갬 (파스트리)
   1. 파스트리 파서라는걸 이용해 처리하고 문법적으로 문제가 되어있을 경우 이단계에서 걸러짐
   2. **결국 파스트리 를 이용해 쿼리를 실행한다는게 핵심**

   1. 불필요한 조건 제거 , 단순화&#x20;
   2. 조인 순서 지정&#x20;
   3. 사용 조건 및 인덱스 통계 정보를 이용해 사용할 인덱스 결정

### 풀 테이블 스캔과 풀 인덱스 스캔

풀 테이블 스캔은 테이블의 데이터를 처음부터 끝까지 읽어서 작업을 하는것이다. 이때 인덱스는 읽지 않는다 .&#x20;

옵티 는 다음 조건으로 스캔&#x20;

* 레코드 건수가 작아서 인덱스를 통해 읽는것보다 풀 테이블 하는게 가성비 좋을 경우 (일반적으로 테이블이 페이지 1개로 구성된 경우)
* where , on 등 인덱스를 이용할수있는 적절한 조건이 없는 경우
* 일치하는 레코드 건수가 너무 많은 경우 (뭐 어디서는 25% 라고는 하지만 그것도 통계 정보를 통해서 찾는듯)

일반적으로 풀 테 스 할때 한꺼번에 몇개씩 페이지를 읽어오는 기능 내장 , 단 몇개씩 페이지를 읽어올지에 대한 설정은 없다 .&#x20;

리드 어헤드 : 미리 어떤 영역에 데이터가 앞으로 필요해질거라는 예측해서 미리 디스크에서 읽은 당므 버퍼 풀에 가져다 두는것, 풀 테 스 뿐만 아니라 풀 인덱스 스캔에서도 동일하게 사용된다.



### 병렬 처리

하나의 쿼리를 최대 몇개의 스레드를 이용해서 병렬로 처리 할 지 변경할수있다.&#x20;



#### Using filesort (Order By 처리)

insert, update , delete 는 이미 인덱스가 정렬되어 있어 순서대로 읽기만 하면 되무로 빠르다 . 단 인덱스 때문에 부가적인 삭제 / 등록 작업 디스크 공간이랑 버퍼가 필요하다&#x20;

Filesort 는 인덱스 생성하지 않으므로 단점이 장점으로 커버된다. 정렬 레코드가 많지 않으면 오히려 filesort 가 처리 되므로 빠를수있다. 단 정렬 작업이 쿼리 실행시 처리 되므로 레코드 대상 건수가 많아지면 응답속도가 느려진다.&#x20;

* 정렬 기준이 너무 많아서 요건별로 인덱스 생성하는것이 불가능
* group by 결과 또는 distinct 같은 처리의 결과를 정렬해야 하는경우&#x20;
* union 임시 테이블 결과를 다시 정렬해야하는 경우&#x20;
* 랜덤한 결과 레코드를 가져와야 하는경우&#x20;

별도 정렬 에 대해 해당 usingfilesort 가 표시 되는지 확인 가능&#x20;



1. 소트 버퍼 (소재 ..? )

정렬을 수행하기 위해 별도의 메모리 공간 사용, 쿼리 실행이 완료 되면 즉시 시스템으로 반납 된다.&#x20;

만약 정렬해야할 레코드 건수가 많아 소트 버퍼로 할당된 공간보다 크다면 어떨까 ?&#x20;

정렬해야할 레코드를 여러 조각으로 나눠서 이 과정에서 임시 저장을 위해 디스크를 사용한다.&#x20;

이 처럼 각 버퍼 크기 만큼 정렬된 레코드를 다시 병합하면서 정렬을 수행해야한다. 이 작업을 멀티 머지라고 표현한다.

소트버퍼는 256 kb 나 8MB 이내로 설정해야 가성비가 좋아진다.&#x20;

단 소트 버퍼는 세션 스토리지 영역이라서 매번 세션마다 나오기 때문에 조심해야한다.&#x20;

단 소트를 사용하면 빠른 성능은 얻을수 없지만 디스크 읽/쓰 사용량을 줄일 수 있다.&#x20;

이것들은 정렬할때 레코드 전체를 소트에 담을지 정렬 기준 칼럼만 소트에 담을 따라 정렬 알고리즘이 달라진다.
