# 데이터 모델과 질의 언어

데이터 모델은 무엇인가 ...

데이터 모델은 문제를 어떻게 생각해야 하는지에 영향을 미친다.&#x20;

데이터의 모델이 있다고 했을때, 이 데이터의 중요한 목적과 정의는 무엇인지가 중요할거같다.

계층형 구조라고 할 경우, 각 계층의 핵심적인 문제는 다음 하위 계층 관점에서 데이터 모델을 표현하는것이다.

* 개발자는 현실을 기반으로 객체나 데이터 구조 그리고 이를 다루는 API 모델링
* 데이터 구조 저장 할때 RDB 테이블이나 ,그래프 모델 같은 범용 데이터 모델로 표현
* 메모리나 디스크 같은 바이트 단위로 표현

결국 최종 목표는 각 계층의 명확한 데이터 모델을 제공해 하위 계층의 복잡성을 숨긴다.

어플리케이션에 적합한 데이터 모델을 선택하는 작업은 중요하다.&#x20;

### 관계형 모델과 문서 모델

RDB : 근본은 비즈니스 데이터 처리에 있다. 관계형 모델의 목표는 정리된 인터페이스 뒤로 구현 세부 사항을 숨기는 것이다.

NOSQL : 대규모 데이터셋이다나 매우 높은 쓰기 처리량 달성을 RDB 보다 뛰어난 확장성 필요, 오픈소스에 대한 선호도 확산. 관계형 스키마의 제한으로 인한 불만과 동적이고 표현력이 풍부한 데이터 모델에 대한 바람

다중 저장소 지속성이 중요한다.

#### 객체 관계형 불일치

RDB 데이터 구조와 와 애플리케이션 코드와 변환하는건 귀찮다.&#x20;

그래서 때때로 json 모델로 저장하여 하는 방법도 적절한 선택이 될수 있다. 다중 테이블 스키마 보다 더 나은 지역성을 갖는다

중복된 데이터를 저장할려면 다대일 관계 가 필요하다. 그렇게 되면 문서 모델에 적합하지 않다.&#x20;

#### document db&#x20;

네트워크 모델 : 코다실 레코드는 여러 부모가 존재한다. 레코드를 접속하는 방법은 최상위 레코드 부터 접그하는 방법이 있다.



#### 결국 rdb 와 오늘날의 문서 데이터베이스

둘을 비교할때 내결함성과 동시성 처리를 포함해 고려해야할 차이점이 많지만 모델 차이점만 집중한다면 ...

문서는 스키마의 유연성 지역성에 기인한 더 나은 성능 때문이랑 , 애플리케이션에서 사용하는 데이터 구조에 더. 가깝기 때문이다. 관계형 모델은 조인, 다대일, 다대다 관계에서 더 잘 지원함

어떤 데이터 모델이 코드를 더 간단하게 할까?

데이터가 문서와 비슷한 구조라면 문서 모델을 사용하는 것이 좋다. 문서와 비슷한 구조를 여러 테이블로 나누어 찣는 방법은 불필요하게 복잡한 애플리케이션 코드를 발생시킨다.

다만 애플리케이션 에서 다대다 관계를 사용한다면 효과가 미흡하다. 비정규화로 조인 줄이기는 가능하지만, 비정규화로 된 데이터 일관성을 유지하기 위해 추가 작업을 해야한다. 애플리케이션에서 다중 요청으로 조인을 흉내낼수있지만, 복잡도 가 안좋다.&#x20;

#### 문서 모델에서 스키마 유연성

스키마가 없다는 뜻은 문서에 포함된 필드의 존재 여부를 보장하지 않는다. 쓰기 스키마와 읽기스키마가 있다.

읽기는 동적 런타임 타입 확인과 유사하고, 쓰기는 정적(컴파일) 타입 확인 과 비슷하다.&#x20;

#### 질의를 위한 데이터 지역성



#### 정리

다대다 관계를 표현하기 에는 트리 구조가 적절하지 않았다. 이를 위해 RDB 모델이 고안되었고, 여기서 고민할 부분은 다음과 같다&#x20;

1. 문서 데이터베이스는 데이터가 문서 자체에 포함돼 있으면서  하나의 문서와 다른 문서 간 관계가 거의 없는 사용 사례를 대상으로 한다.&#x20;
2. 그래프 데이터베이스는 문서 데이터베이스 와는 반대로 모든것이 잠재적으로 관련있다는 전제로 대상을 한다.

세가지 모델 모두 각기 목적에 맞는 다양한 시스템을 보유해야하 하는 이유다.

문서 그래프는 변화하는 요구사항에 맞춰 애플리케이션을 쉽게 변경할수있다는 점이다.&#x20;
